Проект: SNN_Research_Project — "Численные модели взаимодействия и обмена
информацией в нейронных сетях мозга"
Дата анализа: 2026-10-11

====================================================================
МЕТОДОЛОГИЯ
====================================================================
Анализ не ограничен пересказом документации — каждый фреймворк проверен
практически в текущем окружении проекта:
  ОС: Windows 11 Pro (build 26200)
  Python: 3.12.0 (venv: C:\SNN_Research_Project\.venv)
  Проверка: pip install (реальная установка или --dry-run) + разбор
  метаданных пакетов на PyPI (platform tags доступных wheel-файлов).

Это важно: большинство источников в интернете описывают поведение
фреймворков на Linux, а данный проект развёрнут на Windows — платформа
напрямую определяет, какие инструменты реально доступны без WSL/Docker.

====================================================================
1. NEST (nest-simulator)
====================================================================
Упоминается в обзоре: Diesmann & Gewaltig 2001, Gewaltig & Diesmann 2007,
Van Albada et al. 2018 (бенчмарк NEST vs SpiNNaker), Kunkel et al. 2012.

Статус установки: ПРОБЛЕМНО на Windows.
  - На PyPI пакет "nest-simulator" (v3.10.0) публикует wheel-сборки ТОЛЬКО
    для macOS (arm64/x86_64) и Linux (manylinux2014, musllinux).
    Готового wheel под win_amd64 НЕТ.
  - pip install на Windows откатывается на sdist (nest_simulator-3.10.0.tar.gz,
    36.3 МБ) и запускает сборку из исходников через PEP 517. NEST — это
    C++-ядро с Cython-обёрткой; сборка на Windows официально не
    поддерживается проектом (нет собственного CMake-пайплайна под MSVC
    "из коробки", нужны GSL, при MPI-сборке — дополнительно MPI-SDK).
  - Официальная позиция проекта NEST: Windows-пользователям рекомендуется
    WSL2 или Docker-образ nestsim/nest.

Архитектура/парадигма: point-neuron симулятор, ориентированный на
крупномасштабные сети (десятки-сотни тысяч нейронов), декларативный
Python-интерфейс (PyNEST) поверх C++ ядра с планированием событий по
дискретным временным шагам. Встроенные модели: LIF, AdEx, Hodgkin-Huxley
(через iaf_* и hh_psc_alpha), STDP-синапсы "из коробки" (stdp_synapse,
stdp_synapse_hom), multi-compartment через NESTML-расширения.

Сильные стороны:
  + Де-факто стандарт в вычислительной нейронауке для сетей с миллионами
    синапсов (поддержка MPI + многопоточность, HPC-ориентирован).
    Именно поэтому Van Albada et al. используют его как эталон при
    сравнении с нейроморфным железом (SpiNNaker).
  + Готовые реализации STDP, structural plasticity (Diaz-Pier et al. 2016,
    тоже в списке) — то есть раздел "методы обучения" обзора покрывается
    без написания кода вручную.
  + Богатая библиотека готовых моделей связности (из статьи Diaz-Pier —
    автоматическая генерация коннективности).

Слабые стороны для данного проекта:
  - Нет нативной поддержки Windows → либо WSL2, либо Docker, либо смена ОС
    среды разработки. Это организационный, а не научный барьер, но он
    блокирует "pip install и вперёд" именно на этой машине.
  - Избыточен для прототипа из 2-3 взаимодействующих регионов — сильные
    стороны (масштаб, MPI) не нужны на этапе проверки гипотезы.
  - Порог входа выше, чем у Brian2: модели описываются в терминах API
    create()/Connect(), а не произвольными дифф. уравнениями.

====================================================================
2. Brian2
====================================================================
Упоминается в обзоре: Stimberg, Brette & Goodman 2019; Stimberg et al. 2020
(Brian2GeNN — GPU-ускорение); Zimmer et al. 2019 (PyTorch-обёртка для
обучения SNN, концептуально близко).

Статус установки: РАБОТАЕТ без ограничений.
  - pip install brian2 → версия 2.10.1 установлена и импортирована
    успешно за секунды, никаких сборочных ошибок, чистый wheel для
    win_amd64/cp312.
  - Чистая Python/NumPy/Cython-зависимость, компиляция на этапе
    выполнения (генерация и JIT-компиляция C++/Cython кода "на лету"
    под каждую конкретную модель) — работает и на Windows при наличии
    любого C-компилятора, либо в "чистом" numpy-режиме без компиляции
    (медленнее, но без внешних тулчейнов).

Архитектура/парадигма: нейрон и синапс описываются произвольными
дифференциальными уравнениями прямо в Python-коде (symbolic-ish DSL:
eqs = '''dv/dt = (I-v)/tau : volt'''), фреймворк сам генерирует эффективный
исполняемый код. Это прямое попадание в раздел обзора "модели нейронов"
(Hodgkin-Huxley, FitzHugh-Nagumo, Morris-Lecar, Hindmarsh-Rose — все
тривиально выражаются через уравнения, без необходимости искать готовую
реализацию в библиотеке модели).

Сильные стороны:
  + Самый низкий порог входа и самое быстрое прототипирование: новая
    модель нейрона = несколько строк уравнений, а не C++-плагин, как в
    NEST/NEURON.
  + Произвольные правила STDP/BCM/Oja пишутся как on_pre/on_post код
    синапса — то есть весь раздел "методы обучения" из
    Список_литературы.xlsx реализуем без написания отдельных модулей.
  + Встроенные инструменты мониторинга (SpikeMonitor, PopulationRateMonitor,
    StateMonitor) напрямую дают данные для последующего информационно-
    теоретического анализа (Granger causality, transfer entropy — методы
    из работ Baccalá, Dhamala, Ding в обзоре).
  + Активно поддерживается, большое сообщество, документация ориентирована
    на "от уравнения к сети", что соответствует постановке задачи проекта
    (численные модели взаимодействия, а не готовые биологические шаблоны).
  + Путь масштабирования есть: Brian2GeNN позволяет перенести ту же модель
    на GPU без переписывания с нуля, если прототип "выстрелит".

Слабые стороны:
  - Хуже масштабируется на очень большие сети (>10^5-10^6 нейронов) по
    сравнению с NEST — для диссертационного прототипа из нескольких
    регионов это не критично.
  - Для мультирегиональных топологий (network-of-networks, как у Perich &
    Rajan 2020) нет специального API "регионов" — компоновка нескольких
    NeuronGroup/Synapses объектов и межрегиональных связей делается
    руками, но это не является серьёзным препятствием.

====================================================================
3. NEURON
====================================================================
Упоминается в обзоре: Hines & Carnevale 2001 (Список_литературы.xlsx, раздел
"Программные реализации").

Статус установки: НЕ УСТАНАВЛИВАЕТСЯ на Windows через pip.
  - Официальный пакет на PyPI называется "NEURON" (не "neuron" как можно
    было бы предположить по аналогии — важно: PyPI нормализует регистр,
    но сути это не меняет), текущая версия 9.0.2.
  - Проверка метаданных пакета показала wheel-сборки ТОЛЬКО для:
    macOS (x86_64/arm64) и manylinux (x86_64/aarch64) — под cp310-cp314.
    Wheel под win_amd64 отсутствует полностью, в т.ч. под Python 3.12.
  - pip install NEURON на этой машине завершается ошибкой
    "No matching distribution found" — не вопрос версии Python, а
    полное отсутствие сборки под Windows.

Архитектура/парадигма: биофизически детализированный мультикомпартментный
симулятор (кабельная теория, реалистичная морфология дендритов/аксонов),
golden standard для детальных одноклеточных и небольших сетевых моделей
с учётом геометрии нейрона.

Вывод для проекта: на нативном Windows неприменим без WSL2/контейнера.
Даже с WSL2 — NEURON сильно избыточен для задачи "численные модели
обмена информацией между сетями регионов", так как основная ценность
NEURON — морфологическая детализация одной клетки, а не масштаб сети.
Единственный сценарий, где он оправдан: если в проекте по итогам
потребуется проверить, что эффект, найденный на point-neuron модели,
не является артефактом упрощённой морфологии.

====================================================================
4. Nengo (NEF — Neural Engineering Framework)
====================================================================
Упоминается в обзоре: Bekolay et al. 2014 (Nengo 2.0), Eliasmith & Trujillo
2014 ("use and abuse of large-scale brain models" — критическое
переосмысление крупных моделей мозга, концептуально важно для обзора),
Stewart 2012 (технический обзор NEF).

Статус установки: РАБОТАЕТ без ограничений.
  - pip install nengo → версия 4.1.0, чистый "py3-none-any" wheel,
    установка и импорт успешны мгновенно, никаких компиляторов не нужно.

Архитектура/парадигма: принципиально иной подход — Neural Engineering
Framework кодирует информацию через векторные представления ("semantic
pointers"/population coding), а не через точную биофизику мембраны.
Сети состоят из "Ensembles" нейронов, которые коллективно представляют
числа/вектора, и вычисления задаются через функции, транслируемые в
синаптические веса. Использовался для крупнейшей функциональной модели
мозга (Spaun, Eliasmith et al. 2012).

Сильные стороны:
  + Прямое отношение к разделу обзора "представление информации
    (временное кодирование и т.д.)": NEF формализует, как популяционный
    код переводится в вектор и обратно — то есть даёт готовый
    математический аппарат для количественной постановки вопроса
    "сколько информации передаётся между регионами" без ручного
    изобретения метрики.
  + Поддерживает спайковые (LIF) и несаковые нейроны в одной модели —
    удобно для сравнения "абстрактный код vs временной код".
  + Легко описывать многокомпонентные ("мультирегиональные") системы как
    граф Ensemble/Connection — ближе по духу к литературе про
    network-of-networks, чем голый Brian2.

Слабые стороны:
  - Если цель исследования — показать именно биофизически обоснованные
    механизмы (конкретные ионные каналы, конкретная форма STDP), NEF
    слишком абстрагирован от биофизики — это инструмент другого уровня
    описания (алгоритмического, не механистического).
  - Сообщество меньше, чем у Brian2/NEST, специфичная терминология
    (semantic pointers, SPA) добавляет когнитивную нагрузку, если она не
    нужна по сути задачи.

====================================================================
5. PyNN (мета-интерфейс, не отдельный симулятор)
====================================================================
Упоминается в обзоре напрямую строкой "PyNN: общий интерфейс для
нейросетевых симуляторов".

Статус установки: пакет устанавливается (pip install PyNN, версия 0.13.0,
чистый py3-wheel), НО это ТОЛЬКО API-слой.
  - Проверка субмодулей показала backend-адаптеры: nest, neuron, brian2,
    arbor, spiNNaker, mock, hardware.
  - На Windows реально работоспособен только backend "brian2" (и "mock"
    для тестов) — backends "nest" и "neuron" требуют те же самые
    нативные установки, которые на этой машине не собираются (см. п.1 и
    п.3). Таким образом PyNN на Windows фактически превращается в
    "неудобную обёртку над Brian2" — выгода от переносимости кода между
    симуляторами теряется, если доступен только один backend.

Вывод: PyNN имеет смысл только если в будущем проект переедет на Linux/
WSL2 и понадобится буквально запускать ОДНУИ ТУ ЖЕ модель на NEST и на
NEURON для перекрёстной валидации результата (что является хорошей
практикой для публикации, но не обязательным условием для прототипа).

====================================================================
ПОБОЧНО УПОМЯНУТЫЕ В ОБЗОРЕ ИНСТРУМЕНТЫ (беглая проверка)
====================================================================
- GeNN / Brian2GeNN (GPU-ускорение): официальный Python-интерфейс
  распространяется не как типовой PyPI-пакет с готовыми wheel (пакет
  "pygenn" не найден на PyPI), ставится через conda-forge или сборку из
  исходников с CUDA toolkit. На Windows без NVIDIA CUDA + отдельной
  установки неприменим "в одну команду". Актуально только на стадии
  масштабирования прототипа, не на старте.
- The Virtual Brain (tvb-library): чистый Python wheel (2.10.0,
  py3-none-any), ставится без проблем, но назначение другое — это
  симулятор на уровне нейронных масс/коннектома всего мозга (mean-field),
  а не SNN с отдельными спайками. Полезен позже, если понадобится
  сопоставить результат SNN-модели с крупномасштабной mean-field картиной
  (как в работах Schirner et al. 2022 из Лит.обзор.xlsx).

====================================================================
РЕКОМЕНДАЦИЯ ДЛЯ ТЕКУЩЕГО ЭТАПА ПРОЕКТА
====================================================================
Цель проекта по заголовку обзора — "численные модели ВЗАИМОДЕЙСТВИЯ и
ОБМЕНА ИНФОРМАЦИЕЙ" между сетями/регионами, с последующим измерением
этого обмена (судя по наличию в списке литературы методов Granger
causality, transfer entropy, частотно-фазового анализа). Это задача
про:
  (а) быстрое варьирование архитектуры связи между 2+ регионами,
  (б) быстрое варьирование правил обучения/пластичности,
  (в) удобный доступ к спайковым временным рядам для последующего
      информационно-теоретического анализа (Welch, Granger, PDC).

Рекомендация: BRIAN2 как основной фреймворк для прототипа.
  Обоснование:
  1. Единственный из "тяжёлых" симуляторов, который реально работает на
     этой машине без WSL/Docker прямо сейчас (проверено установкой).
  2. Произвольные ODE-модели нейронов закрывают весь раздел "модели
     нейронов" обзора (Hodgkin-Huxley, FitzHugh-Nagumo, Morris-Lecar,
     Hindmarsh-Rose) одним и тем же API, без переключения инструментов.
  3. STDP/BCM/Oja из раздела "методы обучения" реализуются как
     Synapses(..., on_pre=..., on_post=...) — то есть без необходимости
     искать, поддерживает ли библиотека конкретное правило "из коробки".
  4. SpikeMonitor/PopulationRateMonitor дают сырые данные напрямую в
     numpy — следующий шаг (расчёт Granger causality/transfer entropy
     между регионами по методам Baccalá/Dhamala/Ding из обзора) не
     требует конвертации форматов.
  5. При необходимости масштабирования есть прямой путь на GPU
     (Brian2GeNN) без переписывания модели с нуля.

Дополнительно — Nengo стоит держать «на скамейке запасных»: если в ходе
работы станет ясно, что интересен не механизм (конкретная биофизика),
а именно информационно-векторное представление сигнала между регионами
(раздел обзора "представление информации"), NEF-подход Nengo даст готовый
формализм для этого быстрее, чем кодирование той же идеи вручную в Brian2.

NEST и NEURON стоит отложить до момента, когда (если) понадобится либо
(а) масштаб на порядки больше, чем способен эффективно считать Brian2 на
одной машине, либо (б) биофизическая/морфологическая детализация, либо
(в) кросс-валидация результата на independent-реализации для публикации.
В этот момент разумно поднять WSL2 или Docker-контейнер
(nestsim/nest-simulator на Docker Hub) — на нативном Windows они
недостижимы без дополнительного слоя совместимости.

====================================================================
ПРАКТИЧЕСКИЙ СЛЕДУЮЩИЙ ШАГ
====================================================================
В .venv текущего проекта уже установлены и проверены импортом:
  brian2 2.10.1, nengo 4.1.0, PyNN 0.13.0 (backend brian2).
Можно сразу приступать к прототипу: 2 региона (NeuronGroup) с LIF/HH
нейронами, STDP-связь внутри региона, фиксированная/обучаемая
межрегиональная связь, SpikeMonitor на каждый регион → на выходе —
временные ряды для последующего расчёта меры направленного
информационного потока между регионами.
